# 余っていたスマホを、ペットカメラにした

猫を留守番させるとき、様子が見たい。
市販のペットカメラを買えば済む話だが、引き出しに使っていないスマホが眠っていた。
カメラもWi-Fiも付いていて、電源につなげば動き続ける。これを使わない手はない。

作ってみたら、**かかった費用は0円**、**見る側にアプリのインストールは不要**、
**外出先からも見られる**ものになった。

ただし、素直には出来上がらなかった。この記事は、詰まった箇所の記録である。

---

## どう作るかを決める

やりたいことは単純だ。

- スマホのカメラ映像を、PCや別のスマホのブラウザから見る
- 手元からカメラをON/OFFできる
- カメラが繋がっているかどうかが分かる

方式は3つ考えた。

**A. ブラウザだけで作る（WebRTC）**
カメラ側もブラウザでページを開くだけ。映像はスマホとPCが直接やりとりする。

**B. 画像を1枚ずつ送る（MJPEG）**
実装は一番簡単。ただしJavaScriptで毎フレーム圧縮するのでCPUが張り付く。

**C. Androidアプリを作る**
一番きれいに動く。ただしAndroid Studioの導入から始まる。

**Aを選んだ。** 決め手は発熱とバッテリーだった。
常設カメラで一番困るのは「スマホが熱くなって止まる」ことで、
Bのやり方は毎秒15回JavaScriptで画像を圧縮し続けることになる。
Aなら、スマホに元から載っている映像圧縮の専用回路が使われる。

そしてAには、もうひとつ大きな利点があった。
**Cに乗り換えることになっても、サーバとPC側の画面はそのまま使い回せる。**
捨てる作業にならない。

---

## サーバは「引き合わせ」だけをする

WebRTCの面白いところは、**映像がサーバを通らない**ことだ。

```
   カメラのスマホ                    見る端末
        │                              │
        │  ←──── 映像は直接 ────→      │
        │                              │
        └──────────┬───────────────────┘
                   │
              サーバ（引き合わせ役）
```

サーバがするのは、お互いを引き合わせることと、状態を伝えることだけ。
だからPCのCPU使用率はほぼゼロで、遅延も0.2秒程度に収まる。

サーバはPythonで200行ほど。最初はSocket.IOを使おうとしたが、
クライアント側のJavaScriptを外部のCDNから読み込む必要があると分かって、やめた。
**「インターネットが無くても家の中で動く」という前提と噛み合わない。**
ブラウザに元から入っているWebSocketだけで書き直したら、外部依存がゼロになった。

ここまでは順調だった。

## 詰まった話1：黒い画面をクリックしたら、サーバが死んだ

スマホからアクセスしても「このサイトにアクセスできません」と出る。

同じネットワークにいる。ファイアウォールも許可済み。
サーバのプロセスも動いていて、ポートも開いている。なのに繋がらない。

**PC自身から自分のアドレスに繋いでも、繋がらなかった。**
ここでネットワークの問題ではないと分かった。

調べると、こうなっていた。

- TCPの接続要求は受け付けられている（OSが受け取っている）
- でもアプリが一度も取りに行っていない（接続が `CLOSE_WAIT` に溜まっていた）
- プロセスのスレッドは2本だけ。起動から20分でCPU時間は0.38秒。**何もしていない**

原因は、Windowsのコンソール（黒い画面）だった。

**あの黒い画面は、クリックすると文字の選択モードに入る。
そして選択モードの間、画面への出力が止まる。
出力が止まると、書き込もうとしたプログラム自体も止まる。**

サーバは待ち受けを開始した直後、起動メッセージを表示しようとしたところで
固まっていた。ポートは開いているのに、接続を処理する処理が一度も始まっていない。

クリックひとつでペットカメラが無反応になるのは事故なので、2つ手を打った。

1. 起動時に**選択モードそのものを無効にする**
2. 動作中の記録を**画面ではなくファイルに書く**ようにして、
   画面側で何が起きてもサーバが影響を受けないようにする

「動いているはずなのに繋がらない」の原因が、
**プログラムの外側にあった**というのが、いちばん厄介だった。

## 詰まった話2：バグを直したら、別のバグを作った

映像が出るようになった。次はカメラの遠隔ON/OFF。

実装したら、映像が来なくなった。ログを見ると、こう出ていた。

```
InvalidStateError: Failed to execute 'setRemoteDescription'
Called in wrong state: stable
```

原因は競合だった。
カメラ側と視聴側の両方が同時に「接続しよう」と言い出して、
**同じ相手に接続の申し込みが2回飛んでいた。**
先に出した申し込みへの返事が、後から作られた別の接続に当たって壊れていた。

そこで「すでに接続中の相手には、重ねて申し込まない」という判定を入れた。
直った。映像も出た。

**そして、これが次の不具合を生んだ。**

しばらく使っていると、見る側の画面が真っ暗になった。
ページを読み込み直すと直る。でも放っておいても戻らない。

記録を見ると、カメラのスマホのWi-Fiが一瞬切れて、再接続していた。
そのとき何が起きたか。

1. カメラが再接続し、サーバが「この視聴者へ繋ぎ直して」と指示を出す
2. カメラ側の古い接続は、まだ自分を「接続済み」だと思っている
3. さっき入れた判定が働き、**繋ぎ直しを見送る**
4. 視聴側からの要求も、同じ判定で弾かれる
5. 永久に戻らない

**片方だけが切断に気づいている状態は、普通に起きる。**
にもかかわらず、自分の見え方を根拠に相手の要求を却下していた。

直し方はこうした。

- 相手が「壊れている」と申告してきたら、**自分の状態がどうであれ作り直す**
- 申し込みに通し番号を付け、古い返事は捨てる
- 視聴側に見張りを付けた。**映像が実際に進んでいるかを2秒ごとに確認し、
  8秒止まったら作り直しを頼む**

3つ目が効いた。接続が切れたことにブラウザが気づかないまま、
絵だけ止まることがある。状態表示は当てにならない。
**実際に映像が進んでいるかどうかだけが、信用できる指標だった。**

いまは10秒ほどで自動的に復帰する。何もしなくていい。

## 詰まった話3：外からは、状態だけ届いて映像が来ない

家の中では完璧に動くようになった。次は外出先から。

自宅をインターネットに公開するのは避けたかったので、Tailscaleを使った。
自分の端末同士だけを繋ぐ仕組みで、無料。
おまけに正式なHTTPS証明書まで発行してくれるので、
**ブラウザの「安全ではありません」警告が消える。**
これは地味に効く。警告が出るサイトでは、
スマホがカメラの使用許可を記憶してくれないことがあるからだ。

設定して、スマホのWi-Fiを切って、モバイル回線から開いてみた。

```
DEVICE  ONLINE
CAMERA  ON
```

**状態は正しく出ている。でも画面は真っ暗のまま。**

つまり、サーバとのやりとりは通っている。届いていないのは映像だけだ。
映像はサーバを通らず端末同士が直接繋がるので、そこだけが失敗している。

ここで、原因を推測して潰していくのをやめた。
**両端が「自分にはこの経路で届く」と出し合った候補を、
すべてサーバの記録に残すようにした。**

そして分かった。カメラ側が出せる候補が、家の中のアドレス
（`192.168.0.13`）しかなかった。モバイル回線からは届かない。

足りなかったのは**STUN**という仕組みだった。
「私は外からどう見えますか」と問い合わせると、
公開アドレスを教えてくれるサーバがある。無料で公開されている。
映像はそこを通らない。教えてもらうだけだ。

設定に2行足して、再度テスト。

```
採用された経路 自分[srflx 122.133.x.x] -> 相手[prflx ?]
```

映った。

## 詰まった話4：スイッチを、届かない場所に置いた

最後に音声機能を足した。部屋の音も一緒に送れるようにする。
猫の鳴き声が聞こえるのは、見守りとしてかなり大きい。

実装して、動作確認もして、渡した。返ってきた反応はこうだった。

> 音を出す機能、素晴らしいと思うのですが、なぜか実装されていません

記録を確認すると、機能は入っていた。ページも新しいものが配信されていた。
でも使えない。理由はすぐ分かった。

**音を拾うかどうかのスイッチを、カメラ側の端末にしか置いていなかった。**

音は電池を使うので、既定はオフにしていた。オンにするには、
カメラにしているスマホを操作する必要がある。
そのスマホは、猫のいる部屋に置いてある。

見る側の画面には、灰色になった「音声なし」というボタンだけが出ていた。
使えないボタンは、実装されていないのと区別がつかない。

これは技術的な不具合ではない。**設計の見落としだ。**

> 別の部屋にあるカメラの設定を、カメラ本体でしか変えられないのでは意味がない。

作り直した。ボタンは1つで、状態に応じて意味が変わる。

- 音が切れているとき →「音を聞く」（押すとカメラ側に指示が飛び、集音が始まる）
- 聞こえているとき →「音を止める」（消音すると同時に、カメラ側の集音も止めて電池を節約する）

利用者から見れば「聞きたい」「もういい」の2つしかない。
その裏でカメラ端末への指示と手元の消音解除が動く。

### ついでに見つかった、もっと悪い不具合

直している最中に、音を出そうとして断られたとき
**映像まで止まる**ことに気づいた。

ブラウザには「音の出る映像を勝手に再生してはいけない」という決まりがある。
音を出す操作が断られたとき、私のコードは映像の再生ごと巻き添えにしていた。

処理の順番が逆だった。直した考え方はこうだ。

> 音はあれば嬉しいもの。映像は止めてはいけないもの。

まず必ず消音で再生を始め、音はそのあとで best-effort で足す。
断られても映像は流れ続ける。

さらに、案内の出し方も直した。
「タップして再生」という表示が、実際には映像が流れているのに残っていた。
状態変数を見て消すのではなく、**映像が実際に動いている事実を見て消す**ようにした。
ここでも、信用できるのは状態表示ではなく実際の動きだった。

## 詰まった話5：選んだ音と、違う音が鳴る

最後に「カメラ端末から音を鳴らす」機能を足した。
手元のボタンを押すと、猫のいる部屋のスマホから音が出る。反応を見たい。

音源ファイルは持たせず、その場で合成することにした。
配布物が増えず、読み込みに失敗することもない。

作ってみて分かったのは、**驚かせないために効くのは音量ではなく立ち上がりの速さ**
だということだった。同じ大きさでも、いきなり鳴る音はぎょっとする。
30ミリ秒かけてなだらかに立ち上げ、ゆっくり減衰させると、
同じ音量でもずっと穏やかに聞こえる。

連打できない仕様にもした。1.5秒に1回まで。
鳴らす先はペットや子どものいる部屋であって、鳴らし放題にする場所ではない。

音は3種類にした。チャイム、呼びかけ、短いメロディ。
高さと間隔の細かさをずらして、聞き分けられるようにしてある。

### そして、メロディを選んだのにチャイムが鳴った

手元の試聴では正しくメロディが鳴る。でも部屋のスマホからはチャイムが鳴る。

記録を見たら、答えは単純だった。

```
15:41  カメラのスマホがページを読み込む
15:46  私がメロディを追加する
       → カメラのスマホは、追加したファイルを一度も取りに来ていない
```

**カメラ側の画面が古いままだった。** 知らない音の名前を受け取って、
既定のチャイムに落ちていた。

原因は1つではなく、3つ重なっていた。

1. **JavaScriptがキャッシュされていた。**
   キャッシュを止める判定で `application/javascript` だけを見ていたが、
   実際に配信されていたのは `text/javascript` だった。
   種類を並べて書けば、いつか取りこぼす
2. **知らない音を、黙って別の音に差し替えていた。**
   これがいちばん悪い。「選んだ音と違う音が鳴る」は、
   エラーが出ないぶん原因の分かりにくさが群を抜いている
3. **版が食い違っていることに、誰も気づけなかった**

直した。キャッシュは中身で判定するようにした。
知らない音を受け取ったら差し替えず、理由を返すようにした。
そしてカメラ端末が「自分の鳴らせる音の一覧」を申告し、
食い違えば見る側に「カメラ端末が古い画面です」と出るようにした。

**代わりのもので黙って済ませると、壊れていることが見えなくなる。**

## できあがったもの

| | |
|---|---|
| ライブ映像 | 遅延0.1〜0.3秒 |
| 音声 | 部屋の音も聞ける。手元のボタンから遠隔でオン/オフ |
| 呼び出し音 | カメラ端末から音を鳴らす。3種類・音量2段階・手元で試聴できる |
| 遠隔ON/OFF | 手元からカメラを止める・動かす |
| スナップショット | 見ている画面を保存 |
| 画質切替 | 標準 / 省電力（発熱対策） |
| 画面消灯 | カメラ端末の画面を消したまま配信を続ける |
| 自動復帰 | 映像が止まっても10秒ほどで戻る |
| 外出先から | 自宅を公開せずに見られる |

費用は0円。見る側はブラウザだけ（外出先から見る場合はTailscaleのアプリが要る）。

節電では、**カメラ端末の画面を消す**のが一番効いた。
映像のプレビューを描き続けるのが発熱と電力の主因なので、
配信は止めずに描画だけをやめる。1分触らないと自動的に暗くなり、
「● 配信中」とだけ小さく表示される。

## 振り返って

技術的に難しかったのは、実はWebRTCではなかった。
難しかったのは、**壊れ方が静かなこと**だった。

- コンソールをクリックしただけでサーバが止まる。エラーは出ない
- 片側だけが切断に気づいて、永久に復帰しない。エラーは出ない
- 映像の経路が足りない。状態表示は「正常」と出ている
- ボタンが灰色になっている。実装されていないのと区別がつかない
- 選んだ音と違う音が鳴る。エラーは出ない

どれも、**画面上は問題なさそうに見えるのに動かない**という壊れ方をした。
そして原因が分かったのは、推測をやめて実際の記録を見たときだった。

作りながら学んだことを3つ挙げるなら、これになる。

> 自分の状態を根拠に、相手の要求を却下してはいけない。

接続が切れたことに気づくのは、いつも片側が先だ。

> スイッチは、使う人が手を伸ばせる場所に置く。

これは当たり前のことなのに、動くものを作っている最中はきれいに見落とす。
機能が「ある」ことと「使える」ことは違う。

> 代わりのもので黙って済ませない。

動かないより、動いているように見えて違うことをしている方がずっと厄介だ。
分からないときは、分からないと言わせる。

## 使ってみたい方へ

コードはGitHubで公開しています。ペットカメラとしても、
見守りカメラとしても、そのまま使えます。

必要なのは、余っているAndroidスマートフォンと、
サーバ役になるPCだけです。費用はかかりません。

セットアップ手順は README にまとめてあります。
Tailscaleの設定でつまずきやすい点（カメラ側のスマホにも入れること、
Androidのバッテリー最適化を外すこと）も書いてあります。
